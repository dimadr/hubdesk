# План развития HubDesk Mobile

Дата фиксации: 2026-08-18.

## Цель

Сделать мобильный клиент рабочим инструментом инженера без расширения до универсального приложения. Инженер должен:

1. видеть назначенные ему заявки;
2. создавать обычные и внутренние заявки в пределах действующих backend-прав;
3. принимать заявку;
4. переводить ее в работу;
5. редактировать назначенную ему заявку;
6. заполнять чек-лист, добавлять комментарий и фото;
7. завершать заявку.

Backend остается источником бизнес-правил, ACL и FSM. Отдельные мобильные правила не создаются.

## Обязательные правила

- Статусы строго соответствуют backend FSM: `ASSIGNED -> ACCEPTED -> IN_PROGRESS -> COMPLETED`.
- Статус изменяется только через существующий FSM API.
- Инженер видит и изменяет только назначенные ему заявки.
- При создании инженером backend безусловно назначает исполнителем текущего инженера.
- Тип заявки после создания не изменяется.
- Обязательный чек-лист блокирует завершение.
- Существующие desktop- и backend-контракты переиспользуются; отдельный mobile API не создается.
- Интеграция VK в этот этап не входит. В будущем она подключается на backend как канал уведомлений и ссылок.

## Настройка сервера

- При первом запуске адрес сервера вводится вручную.
- Поле адреса при первом запуске пустое; допустим только нейтральный пример в placeholder.
- `192.168.0.178` не используется как значение по умолчанию: это адрес песочницы.
- Адрес проверяется запросом `/api/health`, а не фиктивной попыткой входа.
- После проверки адрес сохраняется на устройстве.
- В настройках должна быть возможность сменить сервер без очистки данных и переустановки приложения.
- Поддерживаются локальный адрес `http://IP:порт` и будущий VDS `https://домен`.
- Все API-запросы используют только сохраненный адрес.

## Этапы реализации

### 1. Резервная копия

- До изменений создать архив `mobile` на сервере.
- Скачать архив на рабочий компьютер.
- Сверить размер и SHA-256.
- База данных и backend-схема на этом этапе не изменяются.

### 2. Синхронизация API-контрактов

- Исправить `TicketResponse` с учетом nullable-полей внутренних заявок.
- Удалить мобильные статусы `ON_THE_WAY`, `ARRIVED`, `REVIEW`.
- Добавить типы для объектов, комментариев, вложений и чек-листов.
- Централизовать получение понятного текста ошибки backend.

### 3. Подключение и авторизация

- Проверять сервер через `/api/health`.
- При `401` очищать AsyncStorage и Zustand и возвращать пользователя на Login.
- Добавить доступную пользователю смену адреса сервера.
- Различать ошибку сети, ошибку прав и пустой результат.

### 4. Навигация

- Основные разделы первой версии: `Заявки` и `Моя доска`.
- Временно скрыть незавершенный раздел `Объекты` и необязательный для основной задачи раздел `Склад`; код не удалять.
- Карточка на доске открывает заявку.
- Drag-and-drop и отдельные правила движения на доске не добавлять.

### 5. Список заявок

- Сохранить поиск и полезные фильтры.
- Добавить пагинацию или дозагрузку через `limit/offset`.
- Добавить кнопку создания заявки.
- Обновлять список после создания, редактирования и изменения статуса.
- Показывать отдельные состояния загрузки, пустого списка и ошибки.

### 6. Создание заявки

Обычная заявка использует поля desktop-формы: тема, объект, описание, тип, приоритет, дедлайн, контактное лицо, телефон и примечание. Список объектов приходит из `/api/locations`; backend ограничивает инженера закрепленными объектами.

Внутренняя заявка содержит только обязательные поля: описание, дополнение по работам, дедлайн и исполнитель. Для инженера исполнитель показан без возможности изменения и подтверждается backend.

### 7. Карточка заявки

- При открытии загружать актуальные данные через `GET /tickets/{id}`.
- Показывать объект, адрес, заказчика, контакты, описание, примечание, дедлайн и статус.
- Загружать комментарии, вложения и чек-лист.
- Телефон сделать доступным для вызова системного приложения звонков.
- Дать возможность добавить обычный комментарий и фотографию.

### 8. Редактирование

- Добавить редактирование только назначенной инженеру заявки.
- Использовать разрешенные backend поля.
- Не позволять инженеру менять исполнителя.
- Для внутренней заявки редактируются только описание, дополнение по работам и дедлайн; исполнитель отображается неизменяемым.

### 9. Чек-лист

- Показывать существующие чек-листы и обязательность полей.
- Поддержать заполнение checkbox, текста и числа.
- Для поля типа `photo` использовать загрузку фотографии к заявке.
- Не добавлять в mobile создание структуры чек-листа.

### 10. Движение и завершение

- `ASSIGNED -> ACCEPTED`: кнопка `Принять`.
- `ACCEPTED -> IN_PROGRESS`: кнопка `Начать работу`.
- `IN_PROGRESS -> COMPLETED`: кнопка `Завершить`.
- После перехода повторно получать заявку с backend.
- Перед завершением проверять обязательные поля чек-листа.
- Комментарий о выполненной работе и завершение отправлять через `POST /tickets/{id}/complete`.
- Не создавать отчет инженера как внутренний комментарий.
- Блокировать повторное нажатие во время запроса.

### 11. Проверка

- Выполнить `tsc --noEmit --incremental false`.
- Проверить подключение к песочнице и смену адреса сервера.
- Проверить вход, истечение токена и возврат на Login.
- На тестовых данных проверить создание обычной и внутренней заявки, редактирование, все переходы FSM, комментарий, фото, чек-лист и завершение.
- Проверить восстановление после потери сети и отсутствие двойных запросов.

### 12. APK

- После приемки изменений выполнить внешнюю сборку через Expo EAS Build с профилем `production`.
- Команда проекта: `eas build --platform android --profile production`.
- Внешнюю сборку запускать только после отдельного подтверждения пользователя.
- Перед распространением production APK заменить debug-подпись на отдельный release-keystore.

## Критерий готовности

Инженер после ручного подключения к выбранному серверу может войти, увидеть все назначенные ему заявки, создать заявку, открыть ее с полной рабочей информацией, изменить разрешенные поля, пройти четыре статуса, заполнить обязательный чек-лист, приложить отчет и фото и успешно завершить заявку. При ошибке сети или отказе backend данные не маскируются под успешную операцию.

## Этап после 3.0RC

Дата фиксации: 2026-08-21.

Рабочая версия 3.0RC сохранена до начала этапа в архиве
`backup/mobile_3.0RC_working_20260821_134615.tar.gz`.

### Тема интерфейса

- Добавить общий переключатель светлой и темной темы.
- Сохранять выбранную тему в AsyncStorage и восстанавливать ее при запуске.
- Применять тему ко всем существующим и новым экранам, включая навигацию.
- Темную тему оставить исходной темой по умолчанию.

### Дополнительные разделы администратора

- Добавить нижний раздел `Еще` с настройкой темы и сервера.
- Только для роли `admin` показывать пункты `Админка`, `Объекты` и `Отчеты`.
- `Админка`: сводные показатели и список пользователей без изменения ролей, удаления,
  модерации, управления почтой и API-ключами.
- `Объекты`: поиск, просмотр карточки объекта и связанных заявок.
- `Отчеты`: основные показатели по заявкам, объектам и инженерам.
- Использовать существующие endpoints и backend ACL; отдельный mobile API не добавлять.

### Канбан

- Начальный масштаб должен помещать все четыре колонки на ширину экрана.
- Добавить явные кнопки уменьшения и увеличения масштаба.
- При увеличении сохранить горизонтальную прокрутку и открытие заявки нажатием.
- Не добавлять drag-and-drop и не менять FSM.

### Проверка этапа

- Выполнить TypeScript-проверку без генерации артефактов.
- Выполнить Expo Doctor.
- Выполнить чистый Android Prebuild во временной копии и подтвердить
  `reactNativeArchitectures=arm64-v8a` и `ndk.abiFilters 'arm64-v8a'`.
- EAS Build запускать только после отдельной команды пользователя.
