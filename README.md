# HubDesk — система управления выездным обслуживанием

Платформа для диспетчеризации заявок, управления объектами, складского учёта и контроля работы выездных инженеров.

**Стек:** FastAPI · PostgreSQL · React · TypeScript · Docker

---

## Возможности

### Заявки

- FSM жизненного цикла: `ASSIGNED → ACCEPTED → IN_PROGRESS → COMPLETED`
- 15 полей: тема, описание, тип работ (ремонт / монтаж / ТО / инспекция / авария), приоритет, объект, оборудование, исполнитель, группа, контакты, плановый выезд, срок исполнения, источник обращения
- Приоритеты: низкий / средний / высокий / критический
- Внутренние и клиентские заявки
- Автоматический расчёт SLA по договору клиента
- Назначение инженера, учёт просрочек, комментарии, вложения, чек-листы
- Два режима просмотра: таблица (drag-n-drop колонок) и карточки
- Фильтрация кликом по ячейкам (статус, приоритет, дата, срок)
- Поиск, сохранённые представления
- Автоматический архив завершённых заявок

### Календарь

- Месячная сетка с заявками по дате исполнения
- Цветовые индикаторы приоритета
- Клик по дню — список заявок на эту дату

### Объекты и оборудование

- Реестр объектов: адрес, контактное лицо (ФИО, телефон, email), договор
- Закреплённый инженер
- Оборудование: серийный номер, модель, QR-код, история обслуживания

### Склад

- Складские документы: приход / перемещение / списание
- FSM документов: `DRAFT → APPROVAL → DELIVERY → ACCOUNTED`
- Инвентаризация только через учтённые документы
- Номенклатура: материалы, продукты, услуги, работы
- Остатки по складам с фильтрацией и поиском
- CRUD складов (администратор)
- Контроль доступа: admin, storekeeper

### Отчёты

- По объектам: всего / открыто / закрыто / просрочено / среднее время
- По заявкам: KPI, раскладка по статусам, приоритетам, типам, SLA %
- По инженерам: назначено / выполнено / в работе / просрочено / среднее время
- Фильтр по диапазону дат

### Роли и права

- Администратор — полный доступ
- Директор — полный доступ (просмотр + управление)
- Диспетчер — заявки, назначение инженеров, отчёты
- Инженер — работа по заявкам, смена статусов, чек-листы
- Кладовщик — складские документы, номенклатура
- Метрологист — склад + вставки
- Бухгалтер — отчёты, объекты, склад (чтение)
- Заказчик — просмотр своих заявок, комментарии
- Наблюдатель — только чтение всех заявок (демо / аудит)
- Саморегистрация с модерацией администратором

### Почта

- IMAP: автоматическое создание заявок из входящих писем
- Фоновый worker с настраиваемым интервалом
- Учётные данные в `.env`, не в базе
- SMTP зарезервирован для уведомлений

### Администрирование

- Дашборд статистики системы
- Управление пользователями (CRUD, пароли, роли)
- Модерация регистраций
- Клиенты (CRUD)
- История действий (history.log)
- Настройка почтового ящика

## Архитектура

Модульный монолит с разделением на слои:

```
backend/
├── src/
│   ├── api/          # Контроллеры (FastAPI роутеры)
│   ├── core/         # FSM-движок, зависимости, исключения
│   ├── models/       # SQLAlchemy 2.0 модели (async)
│   ├── services/     # Бизнес-логика
├── history.log       # Аудит-лог действий
└── .env              # Конфигурация (почта, БД, ключи)

frontend/
├── src/
│   ├── api/          # Axios-клиент с 401-интерсептором
│   ├── components/   # Переиспользуемые компоненты (TicketGrid и др.)
│   ├── pages/        # Страницы приложения
│   └── store/        # Zustand сторы
```

**Ключевые принципы:**
- Смена статуса только через FSM с гардами
- Изменения склада только через учётные документы
- Бизнес-логика не живёт в контроллерах
- Все UI-надписи — на русском языке

## Запуск

### Требования

- Docker и Docker Compose
- PostgreSQL (через Docker или локально)

### Быстрый старт

```bash
cd docker
docker-compose up -d
```

Бэкенд на порту 8002, фронтенд собирается и раздаётся тем же процессом FastAPI.

### Ручной запуск

```bash
# Бэкенд
cd backend
pip install -e .
cp .env.example .env
python3 -m uvicorn src.main:app --host 0.0.0.0 --port 8002

# Фронтенд
cd frontend
npm install
npm run build
```

### Учётные данные

Тестовые пользователи автоматически не создаются. Учётные записи создаются через регистрацию или административный API. Пароли должны содержать не менее 12 символов. Rate limiting: 5 попыток входа на IP за 10 минут.
