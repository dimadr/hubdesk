# HubDesk — система управления выездным обслуживанием

HubDesk — это внутренняя платформа для диспетчеризации заявок, управления объектами обслуживания, складского учёта и контроля работы выездных инженеров. Система построена как модульный монолит с гексагональной архитектурой, что позволяет начать с простоты одного развёртываемого артефакта и при необходимости вырастить отдельные модули в независимые сервисы.

Стек: FastAPI (Python) для бэкенда, PostgreSQL для хранения данных, React (TypeScript) для фронтенда, Redis для кэширования. Всё упаковывается в Docker.

## Основные возможности

### Управление заявками

Центральный модуль системы. Каждая заявка проходит через конечный автомат из семи состояний: Назначена, Принята, В пути, На месте, В работе, Проверка, Завершена. Переходы между состояниями строго контролируются ролевой моделью — инженер может двигать заявку вперёд по цепочке, диспетчер назначает исполнителей, администратор имеет право на любой переход.

Заявка содержит пятнадцать полей: тема, описание, тип работ (ремонт, монтаж, техническое обслуживание, инспекция, аварийный выезд), приоритет, объект, оборудование, исполнитель, группа, контакты на объекте, плановое окно визита, срок исполнения, источник обращения. При выборе объекта контактное лицо и телефон заполняются автоматически из карточки объекта.

В заявку можно добавлять комментарии (публичные и внутренние), чек-листы с полями разных типов (текст, число, флажок, фото, подпись), прикреплять файлы. Чек-лист с обязательными полями блокирует завершение заявки до тех пор, пока все пункты не будут заполнены.

При создании заявки система автоматически рассчитывает SLA-сроки на основе активного договора с клиентом. Контролируется время реакции и время решения. Просроченные заявки выделяются в таблице и доступны отдельной вкладкой.

Таблица заявок поддерживает три режима просмотра: классическая таблица с перетаскиванием и изменением ширины колонок, карточки с цветовой индикацией приоритета и компактное дерево. Поиск по номеру и теме, фильтрация кликом по значениям в ячейках (статус, приоритет, дата). Сохранённые представления позволяют зафиксировать часто используемую комбинацию фильтров и настроек колонок.

Завершённые заявки автоматически уходят в архив и не загромождают основной список. Архив доступен отдельной вкладкой, заявки из него можно просматривать в любой момент.

### Календарь заявок

Месячная сетка с заявками, распределёнными по дате исполнения. Каждая заявка показана компактно: номер, тема, цветовой индикатор приоритета. Текущий день выделен. При клике на день открывается список заявок на эту дату с возможностью быстро оценить загрузку.

### Объекты и оборудование

Реестр объектов обслуживания: название, адрес, контактное лицо (ФИО, телефон, электронная почта), закреплённый инженер, реквизиты и срок действия договора. К объектам привязывается оборудование с серийными номерами, моделями и QR-кодами. Ведётся история обслуживания каждой единицы. Администратор может удалять объекты, если к ним не привязаны заявки.

### Складской учёт

Склад работает через учётные документы трёх типов: приход, перемещение, списание. Каждый документ проходит собственный конечный автомат: Черновик, Согласование, Доставка, Учтён. Только учтённый документ меняет складские остатки. Прямое изменение остатков невозможно — это гарантирует целостность инвентаризации.

Номенклатура разделена на категории: материалы, продукты, услуги, работы. Склады бывают физическими и персональными (инженерские). Администратор может создавать, переименовывать и удалять склады. Удаление склада с ненулевыми остатками запрещено.

На вкладке остатков можно выбрать конкретный склад и выполнить поиск по названию номенклатуры. Клик по складу в общем списке сразу фильтрует остатки по нему.

### Отчёты

Три отчёта с фильтром по диапазону дат создания заявок. Доступны администратору и диспетчеру.

Отчёт по заявкам показывает общую картину: количество заявок, среднее время решения, процент соблюдения SLA, раскладку по статусам, приоритетам и типам работ.

Отчёт по объектам — для каждого объекта: сколько всего заявок, сколько открыто, закрыто, просрочено, среднее время решения.

Отчёт по инженерам — для каждого специалиста: количество назначенных заявок, выполненных, находящихся в работе, просроченных, среднее время решения.

### Ролевая модель

Шесть ролей с чётко определёнными границами ответственности:

Администратор — полный доступ ко всем функциям системы, управление пользователями, клиентами, модерация регистраций, настройка почтового ящика, просмотр истории действий.

Диспетчер — создание и редактирование заявок, назначение инженеров, просмотр всех заявок и отчётов.

Инженер — работа с назначенными ему заявками, изменение статусов по цепочке FSM, заполнение чек-листов, добавление комментариев.

Кладовщик — управление складскими документами, номенклатурой, создание и переименование складов.

Заказчик — просмотр заявок своего клиента, добавление публичных комментариев.

Наблюдатель — режим «только чтение». Видит все заявки, но не может ничего менять: ни статус, ни поля, ни комментарии. Подходит для демонстрации и аудита.

### Регистрация и модерация

Новые пользователи регистрируются самостоятельно через форму входа, обязательно давая согласие на обработку персональных данных. После регистрации учётная запись получает статус «ожидает утверждения» и не может войти в систему. Администратор просматривает заявки во вкладке «Модерация», видит указанную роль и факт согласия, после чего утверждает или отклоняет регистрацию. Назначить себе роль администратора при саморегистрации нельзя.

### Аутентификация

Вход по электронной почте и паролю. Пароли хранятся в базе в виде bcrypt-хешей. После входа выдаётся JWT-токен. При установке флажка «Запомнить меня» токен действует тридцать дней, иначе — четыре часа. Все запросы к API проверяют токен, при истечении срока действия происходит автоматический выход.

### Почта

Фоновый процесс с заданным интервалом подключается к почтовому ящику по IMAP, читает новые письма и создаёт из них заявки. Тема письма становится темой заявки, текст — описанием, адрес отправителя сохраняется в источнике обращения. Отслеживается последний обработанный идентификатор письма (UID), поэтому повторная обработка исключена.

Настройки IMAP (сервер, порт, папка, интервал проверки) задаются через панель администратора. Учётные данные почтового ящика (адрес и пароль) хранятся в конфигурационном файле `.env` и не попадают ни в базу данных, ни в API.

Для отправки уведомлений зарезервирован SMTP-доступ, реализация которого планируется в следующей итерации.

### Административная панель

Шесть вкладок для управления системой. Дашборд показывает ключевые показатели: количество пользователей, клиентов, объектов, складов и статистику по заявкам. Пользователи — таблица с возможностью редактирования имени, почты, роли и пароля, а также удаления учётных записей. Модерация — очередь заявок на регистрацию с кнопками утверждения и отклонения. Клиенты — создание, редактирование и удаление клиентов. История — журнал действий системы с отметками времени и описанием событий. Почта — включение и выключение автосбора, настройка IMAP, кнопка ручной проверки.

### Сотрудники

Страница со списком всех пользователей, их ролями и статусами (активен, ожидает, отклонён). Администратор может добавлять новых сотрудников и удалять существующих. Кнопки добавления и удаления скрыты для всех остальных ролей.

## Техническая архитектура

Бэкенд построен по принципу гексагональной архитектуры. Бизнес-логика сосредоточена в сервисном слое (`services/`) и не зависит от транспортного уровня. API-роутеры (`api/`) выступают в роли адаптеров, преобразуя HTTP-запросы в вызовы сервисов. Модели данных (`models/`) используют SQLAlchemy 2.0 в асинхронном режиме.

Все изменения статусов проходят через конечные автоматы с гардами. Для заявок это семь состояний с линейным движением вперёд и проверкой заполнения чек-листа перед завершением. Для складских документов — четыре состояния с изменением остатков только на этапе учёта.

Фронтенд использует Zustand для управления состоянием, Axios с перехватчиком для автоматического выхода при истечении токена, dnd-kit для перетаскивания колонок таблицы. Таблица заявок оптимизирована: ячейки обёрнуты в React.memo, фильтрация результатов мемоизирована через useMemo, поисковые запросы отменяются через AbortController при быстрой смене фильтров.

Система логирует ключевые действия в текстовый файл `history.log`: создание заявок, смена статусов, назначение инженеров, регистрация и утверждение пользователей.

## Запуск

Требуется Docker и Docker Compose.

```bash
cd docker
docker-compose up -d
```

После запуска контейнеров бэкенд доступен на порту 8002, фронтенд собирается в статические файлы и раздаётся тем же процессом FastAPI. При первом запуске база наполняется тестовыми данными, описанными ниже.

Для ручного запуска:

```bash
# Бэкенд
cd backend
pip install -r requirements.txt
cp .env.example .env          # настроить DATABASE_URL, секретный ключ, почту
python3 -m uvicorn src.main:app --host 0.0.0.0 --port 8002

# Фронтенд
cd frontend
npm install
npm run build                 # соберёт статику в frontend/dist/
```

При первом запуске создаются восемь пользователей, четыре клиента, восемь объектов, шесть складов и пятнадцать заявок в разных статусах.

## Архитектурные принципы

Система следует трём ключевым ограничениям:

Смена статуса заявки — только через конечный автомат с проверкой роли и гардами. Прямое присваивание статуса в обход FSM невозможно.

Изменение складских остатков — только через учётный документ, прошедший все стадии. Ни один контроллер не имеет права напрямую изменить поле quantity.

Бизнес-логика не размещается в контроллерах. Все решения о допустимости операции принимаются в сервисном слое или на уровне FSM-гардов. Контроллер только принимает запрос, передаёт данные в сервис и возвращает ответ.

## Дорожная карта

В планах развития: светлая тема оформления, полноценная интеграция с почтой для отправки уведомлений, мобильное приложение на React Native с офлайн-режимом и синхронизацией, OAuth2 и единый вход через корпоративные системы, расширенная аналитика с графиками и выгрузкой отчётов, база знаний для самостоятельного решения типовых проблем, автоматическая маршрутизация заявок по ключевым словам и отделам.
